# Build Library และการบันทึกบิลด์

เอกสารนี้แยก **สิ่งที่ผู้ใช้ต้องการ** ออกจาก **ข้อเสนอที่ยังรอเลือก** ก่อนพัฒนาและใช้งานจริง

## เป้าหมายที่ต้องรองรับ

- ผู้เล่นสร้างและบันทึกบิลด์ที่ประกอบด้วย class / job, เลเวล, Growth, Bonus Points, สกิล, บัฟ, อุปกรณ์, Refine / Compound, ไอเทม custom และหมายเหตุได้
- มีที่ดูว่าตอนนี้แต่ละสายมีบิลด์อะไร โดยจัดหมวดเช่น `Build 150–200`, `Build 250+`, `Build Endgame` และค้น / กรองตาม class, job, ช่วงเลเวล และชื่อ
- พิจารณาให้ผู้ใช้ที่ล็อกอินทุกคนเห็นบิลด์ที่บันทึก และพิจารณาว่าควรบังคับล็อกอินตอนใด
- ป้องกันการกดบันทึกซ้ำรัว ๆ และตรวจข้อมูลก่อนบันทึกทั้งฝั่งหน้าจอและฝั่งที่รับข้อมูล

## ข้อเสนอเพื่อหารือ

**แนะนำให้ทดลองจัดบิลด์ได้โดยไม่ล็อกอิน แต่ต้องล็อกอินเมื่อบันทึกขึ้น Build Library** ผู้เล่นใหม่เห็นคุณค่าของ Planner ได้ทันที ส่วนบัญชีช่วยระบุเจ้าของ กู้ข้อมูลข้ามอุปกรณ์ และจัดการการแก้ไข; ระหว่างล็อกอินควรเก็บ draft ในเครื่องไว้และกลับมาบันทึกต่อได้

สำหรับการมองเห็น เสนอให้แยกคำว่า **บันทึกฉบับส่วนตัว** กับ **เผยแพร่ใน Library**:

1. บิลด์ส่วนตัว: เจ้าของเห็นและซิงก์ข้ามอุปกรณ์ได้
2. บิลด์ที่เผยแพร่: ผู้ใช้ที่ล็อกอินทุกคนค้นและเปิดดูได้ตามที่เสนอ เจ้าของแก้ / ถอนเผยแพร่ได้; ผู้ดูทำสำเนาเป็นบิลด์ของตัวเองได้โดยไม่เปลี่ยนต้นฉบับ

การมีขั้นเผยแพร่แยกช่วยให้ผู้เล่นทดลองหลายรอบก่อนให้ทุกคนเห็น แต่ถ้าต้องการให้ **ทุกครั้งที่กดบันทึก ทุกคนที่ล็อกอินเห็นทันที** ก็ทำได้โดยใช้ปุ่มและข้อความแจ้งที่ระบุชัดเจน กติกานี้ยังรอเจ้าของโปรเจกต์เลือก; ห้ามนำข้อเสนอข้างต้นไปตีความว่าเลือกแล้ว

## โครงสร้าง Library ที่แนะนำ

- เส้นทางหลัก: เลือก class → job / สาย → รายการบิลด์ พร้อมกรองช่วงเลเวล / สถานะเซิร์ฟเวอร์ และค้นชื่อ
- ช่วง `150–200`, `250+`, `Endgame` เป็นตัวอย่างป้ายจากผู้ใช้: **ยังไม่กำหนดช่วงสุดท้าย** เพราะมีช่วง 201–249 ที่ไม่ครอบคลุม และ `Endgame` อาจทับกับ `250+` ต้องตัดสินใจว่าจะเป็นช่วงเลเวลที่ไม่ทับกันหรือเป็นแท็กอิสระ
- การ์ดแสดงชื่อบิลด์, class / job, เลเวลหรือช่วงที่ผู้สร้างตั้งใจ, แท็ก, ชื่อแสดงผลที่ผู้ใช้เลือก, วันที่อัปเดต และข้อมูลเวอร์ชัน / สถานะตรวจสอบที่จำเป็น
- เปิดดูรายละเอียดอุปกรณ์ทุกช่อง สกิล บัฟ สเตตัส และหมายเหตุ โดยระบุว่าสูตร / ข้อมูลไหนยังไม่ยืนยัน; บิลด์ custom ต้องพกข้อมูลไอเทมที่จำเป็น ไม่พึ่งชื่ออย่างเดียว
- กรองผลแบบแบ่งหน้าและค้นตาม index; ตัดสินใจภายหลังเรื่องเรียงล่าสุด / ความนิยม และหลีกเลี่ยงการนำข้อมูลส่วนตัว เช่นอีเมลหรือ UID ไปแสดง

## การบันทึกและป้องกันซ้ำ

### ฝั่ง UI

- ตรวจชื่อที่ไม่ว่างและความยาว, class / job ที่สอดคล้องกัน, เลเวลในช่วงที่กำหนด, Growth และ Bonus Points ถูกกติกา, ช่องอุปกรณ์ / จำนวนช่อง Compound และค่าตัวเลขเป็นค่าจำกัดที่ถูกชนิด
- แสดงข้อผิดพลาดข้างช่องที่แก้ได้; หากข้อมูลเกมบางส่วนยังไม่ครบ ให้แสดงสถานะรอตรวจแทนการตั้งเงื่อนไขผิด ๆ
- เมื่อส่งบันทึก ให้ disable ปุ่มและแสดงสถานะกำลังบันทึกจนสำเร็จ / ล้มเหลว; กดซ้ำระหว่าง pending ไม่สร้างคำขอใหม่ และผู้ใช้ลองใหม่ได้หลังข้อผิดพลาด
- ตรวจการเปลี่ยนแปลงก่อนส่งซ้ำ หากไม่มีข้อมูลเปลี่ยนให้แจ้งว่าไม่มีการแก้ไข; ใช้ cooldown สั้นตามค่าที่ตั้งได้หลังวัดการใช้งาน ไม่ยึดเลขเวลาเฉพาะเป็นกติกาที่ตกลงแล้ว

### ฝั่งเซิร์ฟเวอร์ / ฐานข้อมูล

- การ disable ปุ่มเป็นเพียง UX: ต้องตรวจซ้ำฝั่งที่เชื่อถือได้เรื่องสิทธิ์เจ้าของ, schema / เวอร์ชัน, ความยาวและขนาด payload, ช่วงตัวเลข, ความสอดคล้องของข้อมูล และสิทธิ์เผยแพร่
- ใช้รหัสคำขอหรือ idempotency key สำหรับการสร้าง เพื่อให้ retry จากเครือข่ายไม่สร้างบิลด์ซ้ำ; การแก้ใช้ ID เดิมและ revision / updatedAt เพื่อแจ้งชนกันระหว่างอุปกรณ์
- ป้องกันการส่งถี่จากหลายแท็บหรือเรียกตรงด้วย rate limit / quota ที่เหมาะสมใน trusted backend หรือบริการที่รองรับ ตรวจผลกระทบ Firestore costs; อย่าอ้างว่า client cooldown หรือ Firestore rules เพียงอย่างเดียวเป็น rate limiter ที่เชื่อถือได้
- ออกแบบกรณี offline, timeout, retry, save สำเร็จแต่ response หาย, conflict, ลบ / ถอนเผยแพร่ และข้อมูลอุปกรณ์ custom โดยไม่สูญข้อมูล
- ห้ามรับผลดาเมจหรือสเตตัสรวมจาก client เป็นความจริงที่เชื่อถือได้โดยไม่ตรวจ / คำนวณใหม่ตามสูตรเวอร์ชันที่รองรับ

## สิทธิ์และข้อมูลเดิม

- ปัจจุบัน Guide เก็บในเบราว์เซอร์; cloud sync ยังไม่รวม Build และ Friends ยังไม่แสดง Build
- `users/{uid}` เดิมจำกัดเจ้าของ ส่วน `profiles/{code}` ให้ผู้ล็อกอินที่รู้รหัสอ่านได้ ไม่ได้พิสูจน์ว่าจำกัดเฉพาะเพื่อน การทำ Library ทุกคนที่ล็อกอินเห็นต้องออกแบบ collection, queries และ Firestore Security Rules ใหม่ พร้อมทดสอบสิทธิ์อ่าน / เขียน / ถอนเผยแพร่
- แยกข้อมูลส่วนตัวจากข้อมูลที่เผยแพร่; ประกาศให้ผู้ใช้รู้ว่าเมื่อเผยแพร่ผู้ล็อกอินอื่นเห็นอะไรบ้าง
- การเปลี่ยน `firestore.rules` ใน repo ไม่ทำให้ Firebase เปลี่ยนโดยอัตโนมัติ ต้องมีขั้นทดสอบและเผยแพร่ rules แยก

## คำถามที่ต้องตกลงก่อนพัฒนา

1. บันทึกทุกครั้งเผยแพร่ให้ผู้ล็อกอินทุกคนเห็นทันที หรือแยกบันทึกส่วนตัวกับปุ่มเผยแพร่?
2. ช่วงเลเวลเป็นหมวดไม่ทับกันอย่างไร และ `Endgame` เป็นช่วงหรือแท็ก?
3. ผู้ใช้ทั่วไปแก้ / ถอนเผยแพร่ / ลบบิลด์ตนเองได้แค่ไหน และต้องมีวิธีรายงานข้อมูลผิดหรือไม่?
4. การทดลองแบบไม่ล็อกอินเก็บ draft ในเครื่องนานเท่าใด และเมื่อเปลี่ยนอุปกรณ์ต้องการนำเข้าอย่างไร?
