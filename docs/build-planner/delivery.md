# ลำดับงานและการตรวจรับ

## ลำดับที่เสนอ

1. ตกลงกติกา Build Library / การล็อกอินและการมองเห็นตาม [build-library.md](build-library.md)
2. ออกแบบ schema บิลด์ที่มี version, ID ไอเทม, instance modifications, custom items, skills / buffs และ provenance พร้อมวิธีอ่านข้อมูลเก่า
3. จัดข้อมูลอุปกรณ์จาก client ที่แกะไว้เป็นฐานกลาง ตรวจ class / slot, element และแยกค่าจริง / ไม่ยืนยัน
4. ตรวจค่าตั้งต้น Growth, Bonus และการปัดจากตัวอย่างจริงหลายชุด ก่อนเรียกตัวเลขหน้า `Base Stat` ที่ครบถ้วน
5. ทำ Planner รุ่นแรก: เลือกตัวละครและของ, ปรับแต่ง, สร้าง custom, สรุปแหล่งค่า, บันทึก / นำเข้าเฉพาะบิลด์; รักษาข้อมูล Guide ที่มีอยู่
6. พัฒนา Build Library ตามสิทธิ์ที่ตกลง พร้อม validation / idempotency / การป้องกันคำขอถี่ที่เชื่อถือได้
7. เพิ่ม Buff Config ตาม class และสูตรที่ตรวจแล้ว, เทียบอุปกรณ์รายชิ้น / ทั้งเซ็ต และ Battle Summary ตามข้อมูลที่ตรวจได้จริง

## เกณฑ์ตรวจ

- ผลรวมอุปกรณ์, Refine / Compound, บัฟ และธาตุมีกรณีทดสอบที่ใช้ค่าจริงและแยกแหล่งที่มา รวมถึง negative / zero / rounding / custom
- เปรียบเทียบบิลด์ A/B ต้องไม่เปลี่ยนต้นฉบับ; แสดงชัดเมื่อค่าที่ไม่รองรับไม่ได้รวม
- ตรวจการบันทึกซ้ำ, ล็อกอิน, สิทธิ์เจ้าของ / ผู้ชม, validation ฝั่ง server, retry / idempotency, conflict ข้ามอุปกรณ์ และนำเข้า custom พร้อมบิลด์
- ตรวจ UI มือถือ / เดสก์ท็อป, คีย์บอร์ด, การแตะเปรียบเทียบ, สถานะโหลด / ผิดพลาด และข้อมูลที่ไม่มีรูป / ไม่มีสูตร
- สูตรสกิลและบอสต้องมีตัวอย่างในเกมหลายกรณี ครอบคลุมธาตุและป้องกัน พร้อมระบุว่า server / เวอร์ชันใด
- เมื่อแก้ข้อมูลเว็บรัน `node scripts/validate.js` และ tests ที่เกี่ยวข้องตาม `CLAUDE.md`; การเปลี่ยน rules ต้องทดสอบและเผยแพร่ Firestore rules แยก

## เดโมและขอบเขตเอกสาร

`planner-demo/` เป็นต้นแบบทดลองในเครื่อง มีข้อจำกัดที่ระบุในหน้า ไม่ใช่การยืนยันสูตรหรือ release บน GitHub Pages แผนเอกสารนี้ไม่เปลี่ยนพฤติกรรมเดโมหรือเผยแพร่เว็บ
